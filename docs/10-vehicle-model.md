# Vehicle and Train Model

## Overview

A **train** is a `std::vector<Vehicle>` assembled at runtime from individual vehicle definitions stored in JSON. Vehicle definitions are the canonical source; train compositions reference vehicle `gID`s. This separates the fleet registry from session-specific consists.

## Vehicle definition

Each vehicle is an individual unit with a unique `gID`.

### JSON schema

```json
{
  "gID":              "VEH-GGO-ET22-001-0000001",
  "pID":              "ET22-001",
  "type":             "LOCOMOTIVE",
  "subtype":          "ELECTRIC",
  "displayName":      "ET22-001",
  "lengthM":          19.24,
  "axleCount":        6,
  "massEmptyT":       84.0,
  "massGrossT":       null,
  "maxSpeedKmh":      125,
  "brakingLambdaPct": 100,
  "powerKW":          2000.0,
  "tractionForceKN":  196.0
}
```

For a loaded freight wagon the same fields look like this:

```json
{
  "gID":              "VEH-GGO-403Z-001-0000050",
  "pID":              "403Z-001",
  "type":             "FREIGHT_WAGON",
  "subtype":          "COVERED",
  "displayName":      "403Z-001",
  "lengthM":          14.02,
  "axleCount":        4,
  "massEmptyT":       22.0,
  "massGrossT":       58.0,
  "maxSpeedKmh":      100,
  "brakingLambdaPct": 65,
  "powerKW":          null,
  "tractionForceKN":  null
}
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `gID` | string | yes | generated by `generateGID` |
| `pID` | string | yes | operational number |
| `type` | string | yes | see table below |
| `subtype` | string | depends | required for `LOCOMOTIVE`, `EMU_UNIT`, `FREIGHT_WAGON` |
| `displayName` | string | yes | |
| `lengthM` | float | yes | over buffers |
| `axleCount` | int | yes | |
| `massEmptyT` | float | yes | tare mass in tonnes |
| `massGrossT` | float\|null | no | gross (loaded) mass; `null` for vehicles that are never loaded (locomotives, passenger wagons); if present, used instead of `massEmptyT` for physics calculations |
| `maxSpeedKmh` | int | yes | design maximum for this vehicle |
| `brakingLambdaPct` | int | yes | UIC braking percentage λ; see Physics section |
| `powerKW` | float\|null | no | `null` for unpowered vehicles |
| `tractionForceKN` | float\|null | no | `null` for unpowered vehicles |

### `type` and `subtype` values

| `type`           | `subtype`                      | Notes                               |
|------------------|--------------------------------|-------------------------------------|
| `LOCOMOTIVE`     | `ELECTRIC` \| `DIESEL` \| `STEAM` |                                  |
| `EMU_UNIT`       | `MOTOR` \| `TRAILER`           | Multiple-unit train car             |
| `PASSENGER_WAGON`| —                              |                                     |
| `FREIGHT_WAGON`  | `FLAT` \| `COVERED` \| `TANK` \| `HOPPER` | |
| `SERVICE_WAGON`  | —                              | Maintenance, snow plough, etc.      |

Fields `powerKW` and `tractionForceKN` are used by the **v2 physics model** and ignored by v1. They must still be present in locomotive definitions so the fleet registry is forward-compatible.

## Train composition

A train composition lists vehicle `gID`s in order from **front to rear**. The engine assembles `std::vector<Vehicle>` by iterating the list and looking up each vehicle definition.

```json
{
  "gID":         "TRN-GGO-IC12345-0000100",
  "pID":         "IC 12345",
  "displayName": "IC 12345 Kraków — Gdynia",
  "vehicles": [
    "VEH-GGO-ET22-001-0000001",
    "VEH-GGO-112A-001-0000010",
    "VEH-GGO-112A-002-0000011",
    "VEH-GGO-112A-003-0000012",
    "VEH-GGO-134A-001-0000020"
  ]
}
```

The engine computes derived properties at load time:

```
effectiveMassT(v) = v.massGrossT  if massGrossT is not null
                    v.massEmptyT  otherwise

total_length_m  = sum of vehicle.lengthM
total_axles     = sum of vehicle.axleCount
total_mass_t    = sum of effectiveMassT(v)          ← physics input
consist_lambda  = sum(v.brakingLambdaPct × effectiveMassT(v)) / total_mass_t
                                                     ← mass-weighted average λ [%]
```

## Axle counting and section occupancy

`It` and `iz` devices count axes, not trains. The engine tracks:

1. When the **leading axle** of the train crosses an `It`/`iz`, the section ahead becomes **occupied**.
2. As each vehicle's axles pass, the device increments its internal axle counter.
3. When the running total equals `train.total_axles`, the **trailing axle** has cleared the device — the section behind becomes **free**.

This mirrors real SRK behavior and makes track section occupancy derived directly from the physical device model, not from train position bookkeeping.

## Physics

### Speed profile shape — trapezoidal motion

Both v1 and v2 produce a **trapezoidal speed profile**: the train accelerates linearly to the target speed, holds it, then decelerates linearly to zero (or to a lower target speed). There is no instant speed change — every transition passes through intermediate values every simulation tick.

```
speed
 │
 v_target ─────────────────────────────┐
 │                                /‾‾‾│‾‾‾\
 │                               /    │     \
 │                              /     │      \
 0 ──────────────────────────────────────────── time
          ↑ acceleration       ↑ hold  ↑ braking
          ramp                        ramp
```

A speed-limit change (entering a new section, signal aspect change) simply sets a new `v_target`. If the new target is lower than current speed, the train begins braking immediately.

---

### V1 — constant acceleration (MVP)

V1 uses fixed per-consist acceleration and braking rates derived from vehicle data. No engine force model; no gradient.

**Consist-level derived values (computed at load time):**

```
total_mass_t     = sum of vehicle.effectiveMassT        (see note below)
consist_lambda   = sum(vehicle.brakingLambdaPct × vehicle.effectiveMassT)
                   ─────────────────────────────────────────────────────
                              total_mass_t

a_decel  = (consist_lambda / 100) × 9.81 × 0.85        [m/s²]
           ↑ λ/100 converts to deceleration force per kg; 0.85 is UIC efficiency factor
a_accel  = configurable constant per session (default: 0.5 m/s²)
           (acceleration in V1 is not physics-derived; it is a tuning parameter)
```

`effectiveMassT` per vehicle:
- If `massGrossT` is not `null`: use `massGrossT`
- Otherwise: use `massEmptyT`

**Tick update:**

```
v_target = min(train.maxSpeedKmh, section.maxSpeedKmh, signal_aspect_speedKmh)  [km/h → m/s]

if v < v_target:  v += a_accel × Δt
if v > v_target:  v -= a_decel × Δt
v = clamp(v, 0, v_target)
```

**Reference `a_decel` values by train type:**

| Train type | λ typical | `a_decel` (η = 0.85) |
|---|---|---|
| EMU (EN57, Flirt, 22WE) | 120–150 % | 1.00–1.25 m/s² |
| Passenger loco + wagons | 100–120 % | 0.83–1.00 m/s² |
| Mixed / regional | 80–100 % | 0.67–0.83 m/s² |
| Freight (loaded) | 50–70 % | 0.42–0.58 m/s² |
| Freight (empty) | 70–90 % | 0.58–0.75 m/s² |

No mass, no gradient, no curve resistance. Suitable for dispatcher training where train dynamics are not the focus.

---

### V2 — power and mass (post-MVP)

V2 replaces the fixed `a_accel` with a force-balance model for traction. Braking is physics-derived from λ (no longer a config constant).

**Traction (acceleration phase):**

```
F_traction  = min(tractionForceKN × 1000,  powerKW × 1000 / max(v, 1.0))   [N]
              (sum across all LOCOMOTIVE and EMU_UNIT MOTOR vehicles in consist)
F_rolling   = total_mass_t × 1000 × 0.002 × 9.81                            [N]
F_gradient  = total_mass_t × 1000 × 9.81 × sin(gradient_permille / 1000)    [N]
F_net       = F_traction − F_rolling − F_gradient
a           = F_net / (total_mass_t × 1000)                                  [m/s²]
```

**Braking phase (service brake):**

```
a_decel = (consist_lambda / 100) × 9.81 × 0.85   [m/s²]
```

Same formula as V1 — braking is always λ-derived in both versions. V2 only improves the traction side.

Regenerative braking and emergency brake are post-v2.

The v1 → v2 switch is a configuration flag per session, not a code branch — the engine selects the physics strategy at startup.

## Open questions

- Q-VEH-1: Should multi-unit (EMU) vehicles define their power across the whole unit or per motor car? Per-unit is simpler for v2 physics.
- Q-VEH-2: Should a single train consist allow multiple locomotives (e.g., double-headed freight)? V1 ignores this; V2 would need to sum `tractionForceKN` across all `LOCOMOTIVE` entries.
- ~~Q-VEH-3~~: **Resolved.** Freight wagons carry `massGrossT` (loaded mass) and `massEmptyT` (tare). The engine uses `massGrossT` when present, `massEmptyT` otherwise. `brakingLambdaPct` covers the loaded/empty braking difference — a loaded wagon has a lower λ, so `a_decel` is automatically smaller.
