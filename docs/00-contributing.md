# Contributing Guide

This guide explains how to set up your computer for development and how to work with the repository. It is written for people who may not have programmed before. Read it from top to bottom the first time; afterwards use it as a reference.

---

## What is this project technically?

The simulator is written in **C++**. C++ is a compiled language — you write source code (plain text files ending in `.cpp` or `.h`), then a program called a **compiler** translates that text into an executable that your computer can run.

Because C++ code needs to be compiled before it can be run, you need to install a few tools first. This is a one-time setup.

---

## Glossary — terms you will encounter

| Term | Plain-language explanation |
|---|---|
| **Repository (repo)** | The project folder, including its full history of changes, hosted on GitHub |
| **Git** | A program that tracks changes to files over time and lets multiple people work on the same code without overwriting each other's work |
| **Clone** | Downloading a copy of the repository to your computer |
| **Commit** | A saved snapshot of your changes, with a message explaining what you changed |
| **Branch** | A separate line of development; think of it as a working copy where you can make changes without affecting the main code |
| **Pull request (PR)** | A request to merge your branch's changes into the main code; others can review it first |
| **Compiler** | Translates C++ source code into a runnable program |
| **CMake** | A tool that reads the project's build instructions and tells the compiler what to do and in what order |
| **Ninja** | The actual program that runs the compiler commands generated by CMake; faster than the traditional alternative (Make) |
| **vcpkg** | A package manager for C++ libraries — automatically downloads and compiles third-party code the project depends on (like Qt) |
| **Qt** | A large C++ library that provides windows, buttons, drawing canvas, and network communication |
| **Build** | The process of compiling all the source code into runnable executables |
| **Debug build** | A build with extra information for finding bugs; slower to run but easier to diagnose |
| **Release build** | An optimised build for end users; created by the project owner, not contributors |

## One-time setup — Windows

Follow these steps in order. Each step has a direct download link.

### Step 1 — Install Git

Git is the version control system used to track changes and collaborate.

1. Go to https://git-scm.com/download/win
2. Download the installer (the big green button).
3. Run the installer. On the screen that says **Adjusting your PATH environment**, select **Git from the command line and also from 3rd-party software**. Leave everything else at the default.
4. Finish the installation.

Verify it worked: open **Command Prompt** (press `Win + R`, type `cmd`, press Enter) and type:
```
git --version
```
You should see something like `git version 2.45.0.windows.1`. If you see an error, restart Command Prompt and try again.

### Step 2 — Install Visual Studio 2022 Build Tools

This is the C++ compiler. You do not need the full Visual Studio IDE — just the Build Tools.

1. Go to https://visualstudio.microsoft.com/downloads/
2. Scroll down to **Tools for Visual Studio** and click **Download** next to **Build Tools for Visual Studio 2022**.
3. Run the installer. When the workload selection screen appears, tick **Desktop development with C++**.
4. Click **Install**. This will download around 4–6 GB and takes a while.

### Step 3 — Install CMake

CMake generates the build instructions for the compiler.

1. Go to https://cmake.org/download/
2. Under **Binary distributions**, download the Windows x64 installer (`.msi` file).
3. Run the installer. On the **Install Options** screen, select **Add CMake to the system PATH for all users**.
4. Finish the installation.

Verify: open a **new** Command Prompt (important — the old one does not see the new PATH) and type:
```
cmake --version
```
You should see `cmake version 3.xx.x`. It must be 3.25 or higher.

### Step 4 — Install Ninja

Ninja runs the actual compilation steps. It is a small, fast tool.

Open Command Prompt and type:
```
winget install Ninja-build.Ninja
```
If `winget` is not available on your system (older Windows 10), download `ninja-win.zip` from https://github.com/ninja-build/ninja/releases, extract `ninja.exe`, and place it somewhere that is on your PATH (for example `C:\Windows\System32`, though `C:\tools\ninja\` added to PATH is cleaner).

Verify: open a **new** Command Prompt and type:
```
ninja --version
```

### Step 4a — Install clang-format

clang-format is a code formatter. The repository requires all C++ files to follow a consistent style, and the commit check enforces this automatically — but only if clang-format is installed.

Open Command Prompt and type:
```
winget install LLVM.LLVM
```

Verify: open a **new** Command Prompt and type:
```
clang-format --version
```
You should see `clang-format version 17.x.x` or higher. If the command is not found, add the LLVM `bin` folder (usually `C:\Program Files\LLVM\bin`) to your PATH manually.

Git needs to know your name and email to attach to your commits. Run these two commands in Command Prompt, replacing the values with your own:

```
git config --global user.name "Firstname Lastname"
git config --global user.email "you@example.com"
```

### Step 6 — Set up a GitHub account and SSH key

You need a GitHub account to submit changes. If you do not have one, register at https://github.com.

GitHub requires an SSH key to verify your identity when pushing code. To generate one, open **Git Bash** (installed with Git in Step 1 — find it in the Start Menu) and run:

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

Press Enter three times to accept the defaults (no passphrase is fine for a private machine). Then display your public key:

```bash
cat ~/.ssh/id_ed25519.pub
```

Copy the entire output. Go to https://github.com/settings/keys, click **New SSH key**, paste the key, and save.

Verify: in Git Bash, run:
```bash
ssh -T git@github.com
```
You should see: `Hi username! You've successfully authenticated`.

## One-time setup — Linux (Ubuntu / Debian)

Open a terminal and run:

```bash
sudo apt update
sudo apt install -y \
    git cmake ninja-build \
    gcc g++ \
    clang-format \
    libgl1-mesa-dev \
    pkg-config zip curl unzip tar
```

Verify versions:
```bash
cmake --version   # must be 3.25 or higher
ninja --version
g++ --version     # must be GCC 12 or higher (ships with Ubuntu 22.04+)
```

Configure your Git identity:
```bash
git config --global user.name "Firstname Lastname"
git config --global user.email "you@example.com"
```

Set up an SSH key the same way as described in Windows Step 6 above — the commands are identical in a Linux terminal.

## Downloading the project

Once your tools are installed, download the repository. Open a terminal (or Git Bash on Windows) and run:

```bash
git clone --recurse-submodules git@github.com:kamiltrzcinski/symulator.git
cd symulator
```

`--recurse-submodules` is important — it also downloads vcpkg, which lives inside the repository as a submodule. If you forget it, run this afterwards:

```bash
git submodule update --init --recursive
```

## Building the project

### What happens during a build

1. **CMake** reads `CMakeLists.txt` and figures out what needs to be compiled and in what order.
2. **vcpkg** (triggered by CMake) downloads and compiles all third-party libraries — Qt, nlohmann/json, and others. **This only happens on the very first build and takes 30–60 minutes.** After that, the compiled libraries are cached and reused.
3. **Ninja** runs the compiler on the project's own source files. This takes a few seconds on subsequent builds.

### Build commands — Linux

Run these from inside the `symulator` folder:

```bash
cmake -G Ninja \
      -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_TOOLCHAIN_FILE=vcpkg/scripts/buildsystems/vcpkg.cmake \
      -B build
```

This is the **configure** step — it prepares the build system. You only need to rerun it if you add new files or change `CMakeLists.txt`.

```bash
cmake --build build
```

This is the **compile** step — it builds everything. Run this every time you want to compile your changes.

### Build commands — Windows (Developer Command Prompt for VS 2022)

You must use the **Developer Command Prompt for VS 2022**, not a plain Command Prompt or PowerShell. Find it in the Start Menu under "Visual Studio 2022".

```bat
cmake -G Ninja ^
      -DCMAKE_BUILD_TYPE=Debug ^
      -DCMAKE_TOOLCHAIN_FILE=vcpkg\scripts\buildsystems\vcpkg.cmake ^
      -B build

cmake --build build
```

The commands are identical to Linux; only the line-continuation character differs (`^` instead of `\`) and path separators use backslash.

### Where are the compiled programs?

After a successful build, executables are in the `build/` folder. For example:
- `build/client/symulator-client`
- `build/editor/symulator-editor`

## Running the tests

The project has automated tests. Run them after every change before submitting:

```bash
cd build
ctest --output-on-failure
```

If any test fails, fix it before opening a pull request. Do not submit code with failing tests.

## Automatic commit checks

The repository enforces two rules on every `git commit`. These checks run automatically — you do not need to do anything to enable them. They are activated the first time you run `cmake` (the configure step sets `git config core.hooksPath scripts/git-hooks/` in your local clone).

### What is checked

**Rule 1 — CHANGELOG.md must be staged.**

If you have not added `CHANGELOG.md` to your staged files, the commit is rejected with this message:

```
[pre-commit] FAIL: CHANGELOG.md has not been staged.

  Every commit must include an update to CHANGELOG.md.
  Steps:
    1. Open CHANGELOG.md and add a line describing your change.
    2. git add CHANGELOG.md
    3. git commit ...
```

**Rule 2 — Staged C++ files must comply with clang-format.**

If any staged `.cpp`, `.hpp`, or `.h` file does not match the project's code style (defined in `.clang-format`), the commit is rejected:

```
[pre-commit] FAIL: Staged C++ files are not formatted correctly.

  Run these commands to apply clang-format, re-stage, and commit again:
    git clang-format HEAD
    git add $(git diff --name-only)
    git commit ...
```

If `clang-format` is not installed, this check prints a warning and is skipped — the commit is still allowed. Install clang-format (see setup instructions above) to enable full enforcement.

### When both checks pass

```
[pre-commit] All checks passed.
```

Your commit goes through normally.

### Bypassing for draft commits

If you are making a rough work-in-progress commit on your own branch that you intend to clean up before review:

```bash
git commit --no-verify -m "wip: ..."
```

Do not use `--no-verify` on commits that will be part of a pull request.

---
 a change — step by step

### Step 1 — Get the latest code

Before starting any work, make sure your local copy is up to date:

```bash
git checkout main
git pull
```

**Detecting merge conflicts.** If someone else changed a file you are also working on, `git pull` will report a conflict. You will see output like:

```
CONFLICT (content): Merge conflict in engine/src/placeholder.cpp
Automatic merge failed; fix conflicts and then commit the result.
```

Open the conflicted file. Git marks the problem area with:

```
<<<<<<< HEAD
your version of the line
=======
their version of the line
>>>>>>> main
```

Edit the file to keep the correct code (remove all the `<<<<<<<`, `=======`, and `>>>>>>>` markers), then stage the resolved file with `git add` and run `git commit` to finish the merge.

To see all conflicted files at any time:

```bash
git status
```

Files listed as `both modified` are in conflict.

### Step 2 — Create a branch

Never work directly on `main`. Create a new branch for your change:

```bash
git checkout -b feat/short-description-of-what-you-are-doing
```

Replace `feat/short-description-of-what-you-are-doing` with something descriptive, for example:
- `feat/switch-state-visualisation`
- `fix/client-crash-on-disconnect`
- `docs/improve-setup-guide`

A branch is like a personal copy of the code — your changes stay isolated until they are reviewed.

### Step 3 — Make your changes

Edit files, write code, add tests. Build and run the tests periodically to check that nothing is broken.

### Step 4 — Update CHANGELOG.md

**This is mandatory.** The commit check (see [Automatic commit checks](#automatic-commit-checks) above) will reject your commit if `CHANGELOG.md` is not staged.

Open `CHANGELOG.md`. At the top, below the header, you will find the most recent version block. Either add to it or create a new one. The format is:

```markdown
## [0.2.6] — 2026-05-10

### Added
- Description of what you added.

### Fixed
- Description of what you fixed.
```

Use `### Added` for new things, `### Changed` for modifications to existing behaviour, `### Fixed` for bug fixes, `### Removed` for things that were deleted.

Keep descriptions short but specific — one line per change, saying what changed and where.

### Step 5 — Stage your changes

`git add` tells Git which files to include in the next commit. You must explicitly add every file you want to save:

```bash
git add path/to/changed/file.cpp
git add path/to/another/file.h
git add CHANGELOG.md
```

To see what is staged and what is not:
```bash
git status
```

Files listed under "Changes to be committed" will be included. Files under "Changes not staged" will not.

### Step 6 — Commit

```bash
git commit -m "type(scope): short description of what you did"
```

**Commit message format — this is important:**

```
type(scope): short imperative description
```

The **type** describes the kind of change:

| Type | Use it when |
|---|---|
| `feat` | You added new functionality |
| `fix` | You fixed a bug |
| `docs` | You only changed documentation |
| `refactor` | You restructured code without changing what it does |
| `test` | You added or changed tests |
| `chore` | You changed build configuration, CI settings, or tooling |

The **scope** (optional) is the part of the project you changed: `engine`, `server`, `client`, `editor`, `libtrackview`, `linter`, `db`.

Good examples:
```
feat(engine): implement axle counter occupancy tracking
fix(client): handle TCP reconnect when server restarts
docs: clarify switch modelling in track topology doc
chore(ci): add vcpkg cache to GitHub Actions workflow
```

Bad examples (too vague):
```
fix stuff
update
changes
```

### Step 7 — Push your branch to GitHub

```bash
git push origin feat/short-description-of-what-you-are-doing
```

This uploads your branch to GitHub. You only need to do this once per branch (or again after new commits if you want to update the remote).

### Step 8 — Open a Pull Request

1. Go to https://github.com/kamiltrzcinski/symulator in your browser.
2. GitHub will show a banner: "Your branch had recent pushes — Compare & pull request". Click it.
3. Write a short description of what your pull request does and why.
4. Click **Create pull request**.

After you open a PR, GitHub Actions will automatically build the code on Linux, Windows, and macOS and run the tests. You will see a status indicator on the PR page. Wait for it to turn green before asking for a review. If it turns red, click on the failed job to see the error, fix it, and push again.

## Things you must not do

These actions could cause problems that are hard to undo:

- **Do not push directly to `main`.** Always use a branch and a pull request.
- **Do not create or push version tags** (`v0.1.0`, etc.). Releases are managed by the project owner.
- **Do not commit the `build/` folder.** It is generated and can be gigabytes in size. It is already listed in `.gitignore`.
- **Do not commit `.scendb` project files** you created while testing the editor.
- **Do not run packaging or installer creation commands.** That is the CI pipeline's job.

## Project folder structure (for reference)

```
symulator/
  CMakeLists.txt        ← main build configuration (version read from CHANGELOG.md)
  vcpkg.json            ← list of third-party libraries the project uses
  vcpkg/                ← the vcpkg tool itself (downloaded as part of the repo)
  engine/               ← core simulation logic (runs on the server, no graphics)
  server/               ← session management and client communication
  libtrackview/         ← shared library for drawing the track schematic
  client/               ← the dispatcher’s application (pulpit + EDR views)
  editor/               ← the scenario editor (for building station layouts)
  tests/                ← automated tests
  data/
    vehicle_types/      ← vehicle model/type definitions (shared by engine, client, editor)
    vehicles/           ← individual numbered vehicle instances
    trains/             ← train consist definitions
  scenarios/
    reference/          ← reference station topologies used in integration tests
  proto/                ← FlatBuffers schema files (.fbs)
  docker/               ← docker-compose, Dockerfile, database init script
  scripts/              ← helper scripts (check-changelog.py, git-hooks/)
  docs/                 ← all project documentation (you are here)
  build/                ← generated by CMake; not committed to Git
```
