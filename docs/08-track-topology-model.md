# Track Topology Model

## Object model

### Axle counters

| Device | Placement             | Usage                            |
|--------|-----------------------|----------------------------------|
| `It`   | boundary of a track section | counts axles entering/leaving |
| `iz`   | boundary of a switch  | counts axles entering/leaving |

Both devices are **nodes** in the topology graph. A controlling device (relay/detector) is placed **10 m before each `It`** along the approaching section.

---

### Track section (odcinek torowy)

A directed edge between two `It` nodes.

| Field          | Type    | Notes                                               |
|----------------|---------|-----------------------------------------------------|
| `gID`          | string  | generated by `generateGID("OT", area, pID)`        |
| `pID`          | string  | operational name, e.g. `tor_1a`                    |
| `sID`          | string  | station / LCS identifier                           |
| `startItID`    | string  | gID of the `It` at the start                       |
| `endItID`      | string  | gID of the `It` at the end                         |
| `lengthM`      | float   | metres                                              |
| `electrified`  | bool    |                                                     |
| `maxSpeedKmh`  | int     | line-design maximum; may be overridden by a signal  |
| `signals`      | string[]| gIDs of semaphores whose aspect can restrict speed  |

### Switch (rozjazd)

A ternary node with three `iz` legs: trunk (`pień`), straight (`wprost`), divergent (`odgałęzienie`).

| Field               | Type   | Notes                                            |
|---------------------|--------|--------------------------------------------------|
| `gID`               | string | generated by `generateGID("ZWR", area, pID)`    |
| `pID`               | string | operational name, e.g. `zwr_1`                  |
| `sID`               | string |                                                  |
| `trunkIzID`         | string | gID of the `iz` at the trunk end                |
| `straightIzID`      | string | gID of the `iz` on the straight leg             |
| `divergentIzID`     | string | gID of the `iz` on the divergent leg            |
| `lengthM`           | float  | metres (trunk to tip)                            |
| `maxSpeedStraightKmh` | int  |                                                  |
| `maxSpeedDivergentKmh` | int |                                                  |

---

## Topology as a graph

The layout is a **directed multigraph**:

- **Nodes** — `It` and `iz` devices (axle counters), plus terminal nodes (buffer stops, boundary points).
- **Edges** — track sections and switches connecting those nodes.

This means: occupancy detection and route checking reduce to graph traversal, making it straightforward to count occupied sections between any two points.

## File format recommendation

### Why plain JSON is insufficient at scale

Gdynia Główna Osobowa has roughly:
- ~60 switches
- ~120 track sections / approach tracks
- ~80 signals

A single flat JSON file at that scale reaches 5 000–15 000 lines. Problems:
- No comments — documenting intent of individual objects is impossible.
- No cross-references enforced — a dangling `startItID` silently produces a broken topology.
- Diff noise — the entire file changes on any reorder.
- No schema validation without a separate JSON Schema file.

### Rejected alternatives

| Format      | Verdict                                                                          |
|-------------|----------------------------------------------------------------------------------|
| YAML        | Readable, supports comments, but same structural limitation as JSON for graphs.  |
| TOML        | Good for flat configs; poor for recursive graph structures.                      |
| RailML (XML)| Standard, but extremely verbose; C++ parsing overhead; not editor-friendly.      |
| Custom DSL  | Maximum expressiveness; requires writing and maintaining a lexer/parser.         |

### Recommended approach: split JSON + JSON Schema

**Format: JSON** (resolves open question #4 from `02-system-requirements.md`)  
**Tooling: nlohmann/json** (header-only, C++20-compatible)  
**Validation: JSON Schema** (checked by the editor on load/save)

Split the station into three files to keep each file manageable and independently diffable:

```
stations/
  gdynia_glo/
    meta.json        ← station name, sID, area, CRS coordinates
    topology.json    ← nodes (It, iz, terminals) + edges (track sections, switches)
    objects.json     ← signals, derailers, line blocks and their attributes
```

#### `topology.json` structure

```json
{
  "schemaVersion": 1,
  "nodes": [
    {
      "id": "IT-GGO-tor1a-start-0000001",
      "type": "It",
      "pID": "It_tor1a_A",
      "x": 120.0,
      "y": 45.0
    }
  ],
  "edges": [
    {
      "id": "OT-GGO-tor1a-0000002",
      "type": "track_section",
      "pID": "tor_1a",
      "startItID": "IT-GGO-tor1a-start-0000001",
      "endItID":   "IT-GGO-tor1a-end-0000003",
      "lengthM": 450.0,
      "electrified": true,
      "maxSpeedKmh": 60,
      "signals": []
    },
    {
      "id": "ZWR-GGO-zwr1-0000010",
      "type": "switch",
      "pID": "zwr_1",
      "trunkIzID":     "IZ-GGO-zwr1-trunk-0000007",
      "straightIzID":  "IZ-GGO-zwr1-str-0000008",
      "divergentIzID": "IZ-GGO-zwr1-div-0000009",
      "lengthM": 28.5,
      "maxSpeedStraightKmh": 60,
      "maxSpeedDivergentKmh": 30
    }
  ]
}
```

### Scaling to Gdynia complexity

For a station of the Gdynia Główna Osobowa class the files remain manageable:

| File            | Approx. size       | Lines   |
|-----------------|--------------------|---------|
| `meta.json`     | < 1 kB             | ~20     |
| `topology.json` | ~80 kB             | ~2 000  |
| `objects.json`  | ~50 kB             | ~1 200  |

The editor generates these files; operators never edit them by hand. The split means topology changes (adding a track section) do not dirty the objects file — cleaner git history.

### Editor workflow

1. Editor loads all three files into an in-memory graph.
2. Operator places or connects objects on canvas.
3. Editor assigns `gID` via `generateGID` and writes back to the three files.
4. Engine loads the same files at session start — no conversion step.

### Future option: SQLite as editor-native format

If the editor becomes complex enough (scenario scripting, parametric timetables), migrating to **SQLite** as the editor's native format gives:
- SQL queries for topology analysis (`SELECT` all sections on route X)
- Foreign-key enforcement of `startItID` / `endItID` references
- Single `.db` file per station scenario

Export to the three-file JSON bundle remains the engine's load format. This migration can be deferred to post-MVP without changing the engine interface.
